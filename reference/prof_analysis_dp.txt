4) VERDICT — what stands between "datapacks" and 1ms
---------------------------------------------------------------------
The noise kernel is no longer the bottleneck on datapack worlds. Java stages dominate:
  (1) BIOME RESOLUTION ~43% of worker CPU. MultiNoise RTree over Tectonic's biome
      parameter list per quart + Terralith surface-rule biome conditions + lazy
      codec/tag resolution under them.
  (2) SURFACE RULES ~25%. Datapack rule trees evaluated in Java NoiseBasedChunkGenerator.
  (3) FEATURE/STRUCTURE HEIGHT QUERIES ~12% combined. Each getBaseHeight evaluates the
      (datapack) density function in Java; features add placement overhead.
  (4) Resource churn: codec deserialization + datapack ZIP reads mid-generation.

5) CRITICAL CAVEAT — current datapack world is a chimera
---------------------------------------------------------------------
The native engine generates from EMBEDDED vanilla worldgen JSONs (worldgen.rs
WorldGen::load -> crate::asset()); from the datapack it honors ONLY the resolved
sea level (63 here). Tectonic ships its own noise_settings/overworld.json (100KB,
218 density_function files); Terralith adds its own DFs/noise_settings/surface rules.
=> dp5k terrain SHAPE is vanilla; biomes/surface-rules/features are datapack.
   Speed profile above is representative of the Java-side pipeline cost, but
   bit-parity vs real Terralith/Tectonic vanilla output has NEVER been verified
   (CI judge datapack parity = crussty-custom sea-level pack only).

6) ROADMAP to 1ms with datapacks (datapacks not modified)
---------------------------------------------------------------------
  A. Native datapack-JSON worldgen: parse the pack's noise_settings + density_function +
     noise assets in the Rust engine (json.rs/worldgen.rs/density.rs machinery is already
     generic; missing piece is loading pack assets + bit-parity harness vs Paper Java
     eval of the same JSONs). Without this the world is not the datapack's world.
  B. Native biome/climate takeover (fillBiomesFromNoise + surface biome conditions) —
     biggest single Java line item (~63ms/chunk here).
  C. Native surface-rule engine extended to datapack rule trees (~36ms/chunk).
  D. Native height-query service for feature/structure placement (kill Java
     getBaseHeight density evals).
  E. Pre-resolve datapack objects at boot (no per-chunk codec decode / ZIP reads).
  F. Native fill contention: keep fill threads <= cores-1 on 2-core boxes; measure
     with CRUS_PROFILE=1 for slice/cellfill/material split under load.
